### P2 (8 temuan; disarankan dibereskan atau diterima eksplisit sebelum merge)

**P2-1 — Race penautan identitas berbeda oleh owner yang sama berakhir 500, bukan 409.**
- Lokasi: `internal/store/google_sso.go:124-140`; handler `internal/httpapi/handlers_google.go:183-198`.
- Penyebab: dua request paralel untuk **owner yang sama** tetapi identitas Google berbeda. Yang kalah kena unique violation `UNIQUE(owner_id)`; jalur pemulihan memanggil `FindGoogleIdentity(issuer,subject)` → `ErrGoogleIdentityNotLinked` → diteruskan; handler jatuh ke `databaseOrInternal` (500 `internal_error`).
- Dampak: tidak ada korupsi data (transaksi rollback, tidak ada state parsial); hanya respons 500 yang menyesatkan pada edge langka. Jalur lintas-owner sudah benar (tepat satu 200 + satu 409) dan teruji.
- Bukti belum tertutup tes: `TestConcurrentGoogleLinkHasExactlyOneWinner` hanya menguji dua owner berbeda.
- Rekomendasi: bila `FindGoogleIdentity` mengembalikan `ErrGoogleIdentityNotLinked` setelah unique violation, petakan ke `409 google_already_linked` (atau re-check owner), dan tambahkan tes race same-owner.

**P2-2 — Empat detail error jaringan baru berisi literal `${call.code}` (escaped interpolation).**
- Lokasi (baru di lane ini, tidak ada di base): `app/src/main/java/com/pam/recap/data/backend/BackendSessionRepositoryImpl.kt:309, 378, 421, 437` — `AppError.Network("backend_${'$'}{call.code}")`.
- Dampak: `debugDetail` berisi string literal `${call.code}` alih-alih kode HTTP. Tidak pernah dirender UI (NFR-18; `AppErrorCopy` tidak memakai `debugDetail` untuk `Network`), jadi tidak user-facing, tetapi menghilangkan diagnostik dan merupakan pola escaped-interpolation yang sama kelas dengan temuan audit sebelumnya.
- Rekomendasi: ganti menjadi `"backend_${call.code}"` dan tambahkan assertion kecil pada tes error-code.

**P2-3 — Klaim jumlah tes lama salah (642 vs 640) meski total 676 benar.**
- Lokasi: `README.md:91` dan `docs/PROGRESS_DAILY.md:28` → "676 tes/88 suite/0 gagal (642 tes lama hijau)".
- Bukti: 676 tes = 640 lama + 36 baru (34 SSO + 2 screenshot). `README.md:14` (gate sebelumnya) menyatakan baseline **640 tes/83 suite**, sehingga klaim 642 di baris yang sama bertentangan dengan header repo dan hasil hitung. Suite 88 = 83 + 5 kelas tes baru ✔; angka 34 + 2 screenshot = 36 ✔.
- Dampak: dokumentasi tidak akurat; tidak memengaruhi kode.
- Rekomendasi: koreksi "642" → "640".

**P2-4 — Status implementasi SSO di dokumen masih "belum dijalankan/PLANNED" padahal kode + gate sudah ada.**
- Lokasi: `docs/plans/AUTO_SYNC_CATEGORY_STATUS_PLAN.md:314-315` ("Implementasi dan UAT SSO belum dijalankan"); `docs/PROGRESS_DAILY.md:28` dan `README.md:91` baris yang sama memuat kalimat "Implementasi dan UAT SSO belum dijalankan" padahal baris itu juga melaporkan gate 676 tes/lint/APK; `docs/changes/CR_007…md:57-59` DRAFT-SSO-01..03 berstatus **PLANNED** meski implementasi + gate sudah dijalankan. `CR_007:60` DRAFT-SSO-04 **NOT RUN** sudah jujur.

- Dampak: risiko privasi rendah tapi nyata (nama + alamat yang plausibel di repo privat); bukan secret/token/ID token.

**P2-8 — Saat JWKS TTL kedaluwarsa dan fetch gagal, setiap login menunggu fetch ulang (latensi/amplifikasi).**
- Lokasi: `internal/auth/google.go:196-225` (`key()`), `google.go:227-...` (`fetch` dengan `http.Client` timeout 5 s), konstanta throttle `googleJWKSMinRefetch` hanya dipakai jalur unknown-kid.
- Perilaku: setelah `fetchedAt` lebih tua dari 5 menit, `needsRefresh` selalu true; bila fetch error, kunci lama tetap dipakai (benar untuk ketersediaan) tetapi `fetchedAt` tidak diperbarui, sehingga **setiap** login berikutnya mencoba fetch lagi sambil memegang `v.mu` (serial) hingga maksimum 5 s per request selama gangguan JWKS.
- Dampak: bukan bypass keamanan; risiko latensi/antrean login saat JWKS Google down atau jaringan backend buruk. Volume pilot rendah sehingga dampak terbatas.
- Rekomendasi: terapkan throttle yang sama untuk kegagalan refresh TTL (mis. `lastAttempt` + backoff 15 s), atau perbarui `fetchedAt` parsial dengan masa berlaku singkat saat memakai kunci stale.

### INFO (5 catatan, tidak wajib untuk merge)

**INFO-1 — Tidak ada tes khusus untuk "email sama tidak auto-merge" dan "data/Gmail utuh setelah link".**
Perilaku terbukti dari kode: login hanya lewat `FindGoogleIdentity` (tanpa lookup email) dan `LinkGoogleIdentity` hanya menulis `google_identities`; tes yang ada memastikan identitas tak dikenal tidak membuat user (`httpapi/google_sso_test.go:143-151`) dan akun lain tidak tersentuh (`:254-279`). Namun tidak ada fixture yang menaruh transaksi/Gmail pada owner lalu memverifikasi jumlah baris setelah link, dan tidak ada tes eksplisit "dua owner dengan email sama, sub Google berbeda". Disarankan menambah dua tes regresi tersebut.

**INFO-2 — `GET /v1/auth/google/nonce` tanpa autentikasi dan tanpa rate limit.**
Setiap panggilan menyisipkan satu baris `google_sso_nonces` (dipangkas hanya saat nonce baru dibuat/kedaluwarsa). Untuk pilot volume rendah aman; jika endpoint diekspos publik luas, pertimbangkan rate limit/per-IP quota seperti endpoint publik lain.

**INFO-3 — Artefak APK gate dibangun tanpa client ID.**
0 string `googleusercontent` di dex → membuktikan default aman (tombol tersembunyi) tetapi APK gate **bukan** bukti UI SSO tampil. Bukti UI SSO baru ada di tes Compose/screenshot (unit) dan menunggu UAT perangkat dengan client ID.

**INFO-4 — README backend belum memuat bagian Google SSO.**
Env/endpoint SSO terdokumentasi di `.env.example` + `docs/GOOGLE_SSO_CONTRACT.md`, tetapi `README.md` (bagian env) hanya menyebut Gmail. Operator yang hanya membaca README tidak akan menemukan `GOOGLE_SSO_*`. Tambahkan satu baris tautan ke kontrak.

**INFO-5 — Nonce dibakar sebelum verifikasi (by design).**
Token dengan signature salah tetap menghabiskan nonce; ini disengaja dan diuji (`httpapi/google_sso_test.go:198-204`) agar replay deterministik. Catat di kontrak bila belum (kontrak saat ini menyiratkan nonce sekali pakai, sudah cukup).

- Kode backend + Android untuk Google SSO, linking, dan onboarding Gmail **memenuhi butir mandat yang dapat diuji di level kode/unit/lint**, tanpa P0/P1 dan tanpa regresi tes lama.
- Temuan P2 (terutama P2-1 race 500, P2-2 diagnostik, P2-3..P2-6 akurasi dokumen, P2-7 higiene PII, P2-8 ketahanan JWKS) sebaiknya dibereskan atau diterima eksplisit oleh pemilik sebelum merge ke target final.
- **Laporan ini bukan izin merge dan bukan pernyataan UAT lulus.** Keputusan merge, penjadwalan UAT fisik, dan gate Rp0/Gmail live tetap milik pemilik.
- Auditor tidak mengubah kode/commit/dokumen apa pun selama audit.
