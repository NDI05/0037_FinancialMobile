# UAT admin S4.2 (C21–C25) pada emulator — 23 November 2026

Bukti runtime untuk gerbang admin: gate peran, daftar/cari akun, undangan sekali-tampil,
ubah nama/peran/status dengan CAS revisi, penonaktifan dan guard, serta audit yang dibaca
ulang setelah backend restart. Semua langkah dilakukan pada aplikasi debug yang menunjuk
backend UAT lokal, bukan backend produksi. Bukan bukti perangkat nyata.

## Lingkungan

| Komponen | Nilai |
|---|---|
| APK | `com.pam.recap.debug` dari `:app:assembleDebug -PPAM_BACKEND_BASE_URL=http://127.0.0.1:18090` |
| Backend | `/tmp/pam-uat-api-fixed` dibangun dari `backend-go` HEAD `64d2371` (setelah `a2c5b15`), env `/Users/user/.config/pam/real-uat.env`, port 18090 |
| Database | Turso/libSQL UAT `pam-real-uat-ndi05`; migrasi 015 sudah diterapkan |
| Perangkat | AVD `emulator-5554`, `adb reverse tcp:18090 tcp:18090` |
| Akun sesi aplikasi | `e2e.uat.1122@pam-uat.test` (owner `u_fe3863bab27ae53e0a020df5af3cb6fe`) |
| Akun admin kedua | `<owner-email>` (owner `<owner-id>`) |
| Log | `/tmp/pam-uat-18090-fixed.log` (allow-list: method, route, status) |

Catatan identitas: header Pengaturan menampilkan email kotak surat `<owner-email>`,
tetapi sesi backend yang dipakai aplikasi UAT adalah akun uji `e2e.uat.1122@pam-uat.test`.
Karena itu promosi admin untuk pengujian ini dilakukan pada akun uji tersebut; akun pemilik
`<owner-email>` tetap ADMIN dan ikut tampil di daftar.

## Skenario dan hasil

### 1. Gate peran dan penolakan USER (C25, prasyarat C21–C24) — PASS, termasuk jalur token kedaluwarsa-peran

1. Sebelum promosi, buka `Pengaturan` → `Admin pengguna`. Server membalas `GET /v1/me`
   `200` dengan peran `USER`; layar menampilkan
   `Halaman ini hanya untuk admin. Akun Anda tidak berhak mengelola undangan dan peran.`
   dan tidak ada request admin yang dikirim.
2. Promosikan akun uji dengan CLI operasional:
   `/tmp/pam-admin -promote e2e.uat.1122@pam-uat.test` → `changed=true (promoted)`;
   jalankan ulang → `changed=false (already admin)` (idempoten, tanpa audit kedua). CLI
   menulis audit `bootstrap_admin` dengan `metadata.source="ops-cli"`.
3. Buka ulang layar. Log menunjukkan urutan yang benar untuk token lama:
   `GET /v1/me 401` → `POST /v1/sessions/refresh 200` → `GET /v1/me 200` →
   `GET /v1/admin/accounts 200` → `GET /v1/admin/audit 200`. Layar menampilkan daftar
   `4 akun`, bukan lagi pesan terlarang. Ini membuktikan klien menyegarkan sesi saat
   klaim peran token tidak lagi cocok dengan state server, bukan memaksa logout.

### 2. Daftar, cari, dan detail akun (C22/C25) — PASS

- Daftar awal: `4 akun` dengan baris `Stale` / `uat.admin.invite@pam-uat.test` /
  `ADMIN · ACTIVE · revisi 2`, `UAT Azure` / `e2e.uat.1122@pam-uat.test` /
  `ADMIN · ACTIVE · revisi 1`, `dhika` / `<owner-email>` /
  `ADMIN · ACTIVE · revisi 1`, `UAT Smoke` / `uat-smoke@example.test` /
  `USER · ACTIVE · revisi 2`.
- Pencarian `andhika` (submit) menyaring daftar menjadi satu baris
  `<owner-email>`; menghapus kata kunci memulihkan empat baris.
- `Ubah akun` membuka editor berisi email, `Revisi N`, nama tampilan, chip peran,
  dan chip status — cukup untuk memeriksa detail tanpa endpoint terpisah di UI.

### 3. Undangan sekali-tampil — create terkontrol (C21) — PASS

1. `Undang akun` → email `uat.admin.invite@pam-uat.test`, peran `ADMIN`, masa berlaku `24`
   jam → `Buat undangan`. Log: `POST /v1/admin/invitations 201`.
2. Panel menampilkan token mentah satu kali dengan peringatan
   `Token ini hanya ditampilkan sekali. Salin sekarang; server hanya menyi…` dan ringkasan
   `Undangan untuk uat.admin.invite@pam-uat.test (ADMIN)`. Token tidak muncul lagi setelah
   panel ditutup; daftar akun tidak menampilkan token.
3. Token dipakai melalui `POST /v1/accounts` (bukan route admin) → `201`, akun baru
   `uat.admin.invite@pam-uat.test` lahir dengan peran `ADMIN` sesuai undangan, dan audit
   mencatat `admin.invitation.accept`. Undangan yang sudah dipakai tidak dapat dipakai ulang.

### 4. Ubah akun dengan CAS revisi — update/role/status (C23) — PASS, termasuk konflik

1. Buka editor `uat.admin.invite@pam-uat.test` pada `Revisi 0`.
2. Ubah state dari luar layar (PATCH admin dengan token ADMIN) → server menaikkan revisi
   menjadi 1 dan mengubah nama menjadi `Externally Renamed`.
3. Simpan draf lama dari layar → `PATCH` `409 revision_conflict`; editor tetap terbuka,
   draf tidak hilang, muncul `Akun sudah berubah di tempat lain. Draf Anda tetap tersimpan`
   dengan aksi `Muat ulang data terbaru`.
4. `Muat ulang data terbaru` menampilkan `Revisi 1`; simpan ulang → `PATCH 200`,
   notifikasi `Akun tersimpan.` dan daftar memuat `revisi 2`.
5. Perubahan nama/status juga tercatat di audit (`admin.account.update`,
   `admin.account.deactivate`).

### 5. Penonaktifan dan guard (C24) — PASS

- Nonaktifkan akun lain (`UAT Smoke`, USER): konfirmasi menyebut email target dan
  `semua sesinya…`; `DELETE /v1/admin/accounts/{id}` → `200`, notifikasi
  `Akun dinonaktifkan.`, baris berubah menjadi `USER · SUSPENDED · revisi 1`
  (semua sesi target dicabut; dihitung sebagai suspensi, bukan hapus permanen).
- Nonaktifkan akun sendiri (ADMIN yang sedang login): `DELETE` → `400 invalid_request`,
  UI menampilkan `Permintaan tidak valid.`; akun dan sesi tetap aktif (tidak ada
  self-deactivation).
- Aktifkan kembali `UAT Smoke` lewat editor (`ACTIVE`) → `PATCH 200`,
  baris kembali `USER · ACTIVE · revisi 2`.

### 6. Audit dan readback setelah restart — PASS

- Bagian `Audit admin` menampilkan entri terbaru termasuk `bootstrap_admin`,
  `admin.invitation.create`, `admin.invitation.accept`, `admin.account.update`,
  `admin.account.deactivate`, lengkap dengan aktor → target dan timestamp.
- Filter aksi `admin.account.deactivate` menyaring audit menjadi satu entri yang cocok,
  membuktikan filter dikirim ke server, bukan penyaringan lokal dari satu halaman.
- Pencarian `q` diuji di perangkat; filter peran/status dan cursor hanya diuji pada API/VM,
  bukan lewat UI perangkat pada sesi ini (cursor butuh lebih dari satu halaman akun).
- Backend dihentikan lalu dijalankan ulang dari binary HEAD (`64d2371`), aplikasi dibuka
  ulang: daftar tetap `4 akun` dengan revisi/status yang sama dan audit tetap memuat
  seluruh entri di atas (dibaca dari database, bukan state proses).

## Batasan bukti

- Hanya AVD `emulator-5554`; bukan UAT perangkat nyata dan bukan UAT pemilik.
- Akun uji sintetis di database UAT; tidak ada data keuangan pengguna nyata yang diubah.
- Konflik revisi dipicu sengaja dari luar aplikasi (PATCH admin kedua) untuk menguji jalur
  409; bukan balapan dua perangkat nyata.
- Guard `last_admin` (admin aktif terakhir) tidak diuji ulang di perangkat pada sesi ini;
  jalur itu ditutup oleh test store/HTTP (`ErrLastAdmin` → `409 last_admin`) dan trigger DB.
- Email undangan tidak benar-benar dikirim (undangan dibagikan lewat token satu kali).
